# "어디서 만날래?" — 프로젝트 기획서

> **진실의 원천(Source of Truth)**: 이 파일이 프로젝트 범위·기술 선택·설계 원칙의 기준이다.
> 다른 문서가 이 파일과 충돌하면 이 파일을 우선한다. 방향 변경은 반드시 이 파일에서 시작한다.

---

## 1. 프로젝트 개요

**주제**: 친구들과 모임을 할 때, 각자의 출발 위치를 기반으로 적절한 거리에 있으면서 모임 분위기에 맞는 식당·카페를 추천해주는 서비스.

**RAG의 역할**: 분위기·맥락 기반 추천을 핵심 엔진으로 삼고, 자연어 요구사항 필터링을 그 위에 자연스럽게 얹는다. 단순 거리 계산·카테고리 필터가 아니라, "조용히 얘기 나누기 좋은 곳" 같은 자연어 의도를 이해해 추천하는 것이 차별점.

**핵심 학습 목표**: RAG 파이프라인(임베딩 → 벡터 검색 → 생성)을 직접 구축하고 튜닝해보는 것. 가능한 한 로컬에서 직접 굴려보며 학습 가치를 극대화한다.

---

## 2. 문제 정의

친구들이 모임 장소를 정할 때 겪는 문제:

1. **"어디가 중간이야?" 문제**: N명의 위치가 흩어져 있을 때 공평한 중간 지점을 직관적으로 파악하기 어렵다.
2. **"검색 결과가 내 맥락을 모른다" 문제**: 지도 앱은 거리와 카테고리만 반영하고 "조용히 대화하기 좋은 곳"처럼 분위기·맥락을 이해하지 못한다.
3. **"왜 이 장소를 추천했어?" 문제**: 일반 추천은 추천 근거가 불투명하다. 사용자가 이유를 확인하고 판단할 수 없다.

이 프로젝트는 세 문제를 RAG 파이프라인으로 풀되, **파이프라인 자체를 학습·튜닝하는 과정**에서 실전 역량을 쌓는 것이 목적이다.

---

## 3. 핵심 사용자 시나리오

```
1. 출발지 입력  →  2. 후보지 계산  →  3. RAG 추천  →  4. 결과 표시
   (여러 명 위치)     (중간지점·거리)     (분위기·맥락)     (지도·상호작용)
```

**MVP 시나리오**: 한 명이 참여자 N명의 위치를 텍스트로 입력 → 중간지점 계산 → 분위기 조건 입력 → 가까우면서 분위기가 맞는 식당 추천 → 카카오맵으로 확인.

## 4. 단계별 기능 명세

### 4-1. 출발지 입력

- **MVP**: 한 명이 모임 참여자 N명의 위치를 텍스트로 직접 입력 (지하철역·동네 이름 등).
- 카카오 로컬 API가 텍스트(키워드/주소)를 좌표로 변환.
- **확장(나중)**: 각자 링크를 받아 자기 위치를 입력하는 협업형. (세션 관리·실시간 반영 등 백엔드 복잡도 상승 → MVP 이후로 미룸)

### 4-2. 중간지점·후보지 계산

- **MVP**: N개 좌표의 직선거리 중점(geometric centroid)을 계산.
- **확장(나중)**: 대중교통 이동시간 기준으로 "모두에게 공평한 지점" 계산. (후보별 N명×길찾기 API 호출 → 비용·지연 상승. 직선거리로 후보를 좁힌 뒤 최종 후보에만 이동시간 계산하는 2단계 타협안 고려)

### 4-3. RAG 기반 추천 (프로젝트의 심장)

**인덱싱 단계 (미리 준비)**

- 시드 데이터(분위기 서술 텍스트) → 임베딩 → 벡터 DB 저장(+메타데이터).

**질의 단계 (사용자 요청 시)**

- 자연어 조건 입력 → 하이브리드 스코어링 → LLM 자연어 추천 생성.

#### 데이터 전략

- **크롤링 배제** (약관·차단·유지보수 리스크 회피).
- **장소·좌표**: 카카오 로컬 API (실시간 검색·거리 계산용).
- **구조화 속성**(주차·와이파이·좌석 등): 공공데이터 일부 + 수제작.
- **분위기 서술 텍스트**(벡터 검색 대상): 실재 장소 기반 사실 검수 수제작 시드.
  - ※ 구글 Places는 장소당 리뷰 5개 제한(더 받으려면 사업자 등록·승인 필요), 카카오 로컬 API는 리뷰 본문 미제공. 합법적 API로는 분위기 리뷰 확보 어려움 → 수제작 시드가 현실적 정답.

#### 신뢰성 원칙

- LLM이 지어낸 분위기를 시드로 쓰지 않는다. 실재 장소의 사실 정보를 근거로 분위기 텍스트를 직접 작성·검수.
- RAG 신뢰성의 핵심은 **출처 충실성(faithfulness)과 검증 가능성**. LLM이 검색된 시드 텍스트를 근거로 답하고, 사용자가 원문 근거를 확인할 수 있게 한다.

#### 시드 데이터 구조

- **단위**: 식당 단위로 작성하되, 각 시드에 **좌표값을 메타데이터로 포함**.
  - "잘게 저장하고 필요할 때 집계한다" — 식당 단위로 가지면 언제든 상권으로 묶을 수 있지만, 처음부터 상권으로 뭉치면 다시 쪼갤 수 없음.
- **MVP 범위**: 서울 핵심 상권 4~5개(강남·홍대·성수 등) 선정, 상권당 식당 20~30개씩 시드 제작 (총 100~150개 규모).
  - ※ 시드 제작 부담을 줄이려면, 처음엔 상권 1곳으로 좁혀 파이프라인을 끝까지 돌려본 뒤 나머지로 확장하는 것도 가능.
- **MVP 추천 방식**: 상권 자동 판단 없이 **식당 자체를 직접 추천**.
- **확장(나중)**: 좌표 밀집도 기반 공간 클러스터링으로 상권 단위 추천 제공.

#### 추천 순위: 하이브리드 스코어링

- 분위기 유사도 점수와 거리 점수를 **가중합**하여 최종 순위 결정.
- 거리(km)와 분위기 유사도(0~1)는 스케일이 다르므로 거리도 0~1로 **정규화** 후 합산.
- 가중치는 변수로 빼두고 시드 넣은 뒤 검색해보며 조절. (사용자 슬라이더로 "거리 우선 ↔ 분위기 우선" 체험 기능도 고려)

#### 추천 품질을 좌우하는 두 요인

1. **중간지점 커버리지**: N개 출발지가 흩어지면 중점이 시드 없는 곳에 찍혀 빈손이 될 수 있음.
2. **시드 텍스트 품질**: "좌석 간격 넓고 대화하기 좋다" 같은 분위기 묘사가 실제로 적혀 있어야 분위기 검색이 작동. RAG 품질의 8할이 여기서 갈림.

### 4-4. 결과 표시·상호작용

- 카카오맵에 추천 식당을 핀으로 표시. 출발지들과 중간지점도 함께 표시.
- LLM이 생성한 자연어 추천 설명(추천 이유 + 시드 근거)을 함께 노출.

## 5. MVP 범위 및 제외 범위

### MVP 포함

| 기능 | 설명 |
|------|------|
| 위치 텍스트 입력 | 한 명이 N명의 출발지를 텍스트로 입력 |
| 좌표 변환 | 카카오 로컬 API로 텍스트 → 위경도 |
| 중간지점 계산 | N개 좌표의 직선거리 중점(geometric centroid) |
| 시드 데이터 | 서울 핵심 상권 1곳부터 시작, 식당 20~30개 수제작 |
| 임베딩·인덱싱 | 분위기 텍스트 임베딩 후 Chroma 저장 |
| 하이브리드 스코어링 | 분위기 유사도 + 정규화 거리 가중합 |
| 추천 이유 생성 | 로컬 LLM이 시드 근거 기반으로 생성 |
| 지도 표시 | 카카오맵에 추천 핀과 중간지점 표시 |

### MVP 제외

| 기능 | 제외 이유 | 재검토 시점 |
|------|-----------|-------------|

| 대중교통 기반 중간지점 | N×길찾기 API 비용·지연 | 파이프라인 안정화 후 |
| 상권 자동 클러스터링 | 클러스터링 임계값 튜닝 복잡도 | 시드 100개 이상 확보 후 |
| API 서버 (웹 서비스화) | 프레임워크 미확정, 파이프라인 먼저 | TBD |

| 구성 요소 | 선택 | 비고 |

| 프론트엔드 | **TBD** | — |
| 배포 | **TBD** | — |

**기술 스택 관련 조언**

- 임베딩 모델은 arctic-embed-l-v2.0-ko로 시작하되 교체 가능하게 추상화한다. 파이프라인 완성 후 BGE-m3 등과 비교하는 경험 자체가 핵심 학습 포인트.
- 로컬 생성 LLM은 사양 확인 필수(GPU/VRAM). Qwen3-4B는 4B급이라 부담이 크진 않지만 양자화 버전 포함 사전 확인.
- **4B급 가드레일**: 작은 모델은 환각 위험이 상대적으로 큼. 프롬프트로 "주어진 시드 정보 안에서만 답하라"고 강하게 제약할 것.
- 생성 모듈은 나중에 API로 갈아끼울 수 있게 코드를 추상화해둔다.

## 7. 설계 관통 원칙

- **단순하게 시작, 확장 여지 남기기**: 모든 단계에서 MVP는 가볍게, 고도화는 다음으로.
- **각 도구를 강점에 맞게**: RAG는 분위기 의미 검색에 집중, 변동 잦은 가게 정보는 API에 위임, 거리 제약은 스코어링으로 보장.
- **데이터는 잘게, 집계는 유연하게**: 식당 단위+좌표로 저장해 식당/상권 양쪽 추천 가능성을 모두 열어둠.
