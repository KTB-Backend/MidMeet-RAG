# "어디서 만날래?" — RAG 사이드 프로젝트 기획서

## 1. 프로젝트 개요

**주제**: 친구들과 모임을 할 때, 각자의 출발 위치를 기반으로 적절한 거리에 있으면서 모임 분위기에 맞는 식당·카페를 추천해주는 서비스.

**RAG의 역할**: 분위기·맥락 기반 추천을 핵심 엔진으로 삼고, 자연어 요구사항 필터링을 그 위에 자연스럽게 얹는다. 단순 거리 계산·카테고리 필터가 아니라, "조용히 얘기 나누기 좋은 곳" 같은 자연어 의도를 이해해 추천하는 것이 차별점.

**핵심 학습 목표**: RAG 파이프라인(임베딩 → 벡터 검색 → 생성)을 직접 구축하고 튜닝해보는 것. 가능한 한 로컬에서 직접 굴려보며 학습 가치를 극대화한다.

---

## 2. 핵심 사용자 흐름

```
1. 출발지 입력  →  2. 후보지 계산  →  3. RAG 추천  →  4. 결과 표시
   (여러 명 위치)     (중간지점·거리)     (분위기·맥락)     (지도·상호작용)
```

---

## 3. 단계별 기능 명세

### 3-1. 출발지 입력

- **MVP**: 한 명이 모임 참여자 N명의 위치를 텍스트로 직접 입력 (지하철역·동네 이름 등).
- 카카오 로컬 API가 텍스트(키워드/주소)를 좌표로 변환.
- **확장(나중)**: 각자 링크를 받아 자기 위치를 입력하는 협업형. (세션 관리·실시간 반영 등 백엔드 복잡도 상승 → MVP 이후로 미룸)

### 3-2. 중간지점·후보지 계산

- **MVP**: N개 좌표의 직선거리 중점(geometric centroid)을 계산.
- **확장(나중)**: 대중교통 이동시간 기준으로 "모두에게 공평한 지점" 계산. (후보별 N명×길찾기 API 호출 → 비용·지연 상승. 직선거리로 후보를 좁힌 뒤 최종 후보에만 이동시간 계산하는 2단계 타협안 고려)

### 3-3. RAG 기반 추천 (프로젝트의 심장)

**인덱싱 단계 (미리 준비)**

- 시드 데이터(분위기 서술 텍스트) → 임베딩 → 벡터 DB 저장(+메타데이터).

**질의 단계 (사용자 요청 시)**

- 자연어 조건 입력 → 하이브리드 스코어링 → LLM 자연어 추천 생성.

#### 데이터 전략

- **크롤링 배제** (약관·차단·유지보수 리스크 회피).
- **장소·좌표**: 카카오 로컬 API (실시간 검색·거리 계산용).
- **구조화 속성**(주차·와이파이·좌석 등): 공공데이터 일부 + 수제작.
  - 서울관광재단 식당운영정보: 주차/와이파이/놀이방 등 운영정보 보유.
  - 전북 음식문화플라자 등 일부 공공데이터는 분위기 서술도 포함(지역 한정).
- **분위기 서술 텍스트**(벡터 검색 대상): 실재 장소 기반 사실 검수 수제작 시드.
  - ※ API 리뷰 정책 확인 결과: 구글 Places는 장소당 리뷰 5개 제한(더 받으려면 사업자 등록·승인 필요), 카카오 로컬 API는 리뷰 본문 미제공. → 합법적 API로는 분위기 리뷰 확보 어려움이 확인됨. 수제작 시드가 현실적 정답.

#### 신뢰성 원칙

- LLM이 지어낸 분위기를 시드로 쓰지 않는다. 실재 장소의 사실 정보를 근거로 분위기 텍스트를 직접 작성·검수.
- RAG 신뢰성의 핵심은 "데이터의 완벽한 정확성"보다 **출처 충실성(faithfulness)과 검증 가능성**. LLM이 검색된 시드 텍스트를 근거로 답하고, 사용자가 원문 근거를 확인할 수 있게 한다.

#### 시드 데이터 구조

- **단위**: 식당 단위로 작성하되, 각 시드에 **좌표값을 메타데이터로 포함**.
  - "잘게 저장하고 필요할 때 집계한다" — 정보 손실 없는 데이터 설계. 식당 단위로 가지면 언제든 상권으로 묶을 수 있지만, 처음부터 상권으로 뭉치면 다시 쪼갤 수 없음.
- **MVP 범위**: 서울 핵심 상권 4~5개(강남·홍대·성수 등) 선정, 상권당 식당 20~30개씩 시드 제작 (총 100~150개 규모).
  - ※ 시드 제작 부담을 줄이려면, 처음엔 상권 1곳으로 좁혀 파이프라인을 끝까지 돌려본 뒤 나머지로 확장하는 것도 가능.
- **MVP 추천 방식**: 상권 자동 판단 없이 **식당 자체를 직접 추천**.
- **확장(나중)**: 좌표 밀집도 기반 **공간 클러스터링**으로 "이 식당들이 ○○ 상권에 모여 있어요" 같은 상권 단위 추천도 제공. (클러스터링 임계값 튜닝이 까다로워 MVP에서 제외)

#### 추천 순위: 하이브리드 스코어링

- 분위기 유사도 점수와 거리 점수를 **가중합**하여 최종 순위 결정 (예: 분위기 0.7 × 거리 0.3).
- "거리 필터를 먼저 할지"의 순서 문제: 데이터가 작아(100~150개) 순서에 따른 성능 차이는 미미. 핵심은 "거리 제약을 추천에 반드시 반영"하는 것 — 안 그러면 멀어서 못 가는 추천이 섞임. 가중합 방식이 이 제약을 자연스럽게 반영하며 "조금 멀어도 분위기 압도적인 곳"과 "가깝고 무난한 곳"을 저울질.
- **구현 팁**:
  - 가중치는 변수로 빼두고 시드 넣은 뒤 검색해보며 조절. (사용자 슬라이더로 "거리 우선 ↔ 분위기 우선" 체험 기능도 고려)
  - 거리(km)와 분위기 유사도(0~1)는 스케일이 다르므로 거리도 0~1로 **정규화** 후 합산 (예: 반경 3km=1점, 멀수록 0에 수렴).

#### 추천 품질을 좌우하는 두 요인 (RAG 구조 외)

1. **중간지점 커버리지**: N개 출발지가 흩어지면 중점이 시드 없는 곳에 찍혀 빈손이 될 수 있음. 시드를 깐 상권과 동떨어지지 않아야 함.
2. **시드 텍스트 품질**: "좌석 간격 넓고 대화하기 좋다" 같은 분위기 묘사가 실제로 적혀 있어야 분위기 검색이 작동. 단순 사실 나열뿐이면 매칭 근거 없음. RAG 품질의 8할이 여기서 갈림.

### 3-4. 결과 표시·상호작용

- 카카오맵에 추천 식당을 핀으로 표시. 출발지들과 중간지점도 함께 표시해 "중간지점이 여기, 추천 식당이 이 근처" 그림 제공.
- LLM이 생성한 자연어 추천 설명(추천 이유 + 시드 근거)을 함께 노출.

## 4. 기술 스택

| 구성 요소           | 선택                                                  | 비고                                                         |
| ------------------- | ----------------------------------------------------- | ------------------------------------------------------------ |
| 개발 언어           | **Python 3.11**                                       | ML 라이브러리(PyTorch·transformers·sentence-transformers) 호환성이 가장 안정적인 "단맛 구간". 3.10도 안전, 3.12+는 패키지 빌드가 늦어 설치 마찰 우려 |
| 장소·좌표·가게 검색 | 카카오 로컬 API                                       | 실시간, 최신 가게 정보                                       |
| 임베딩 모델         | **dragonkue/snowflake-arctic-embed-l-v2.0-ko** (로컬) | 한국어 검색 특화, 7개 한국어 검색 벤치마크 SOTA. 짧은 구 질의("조용한 곳") 처리에 강함. MRL 압축 지원(4배 축소 시 품질 저하 3% 미만). 가중치 약 2.27GB, Apache-2.0. BGE-m3는 비교 후보 |
| 벡터 DB             | Chroma                                                | 임베디드·경량, 메타데이터 필터 지원. 우리 규모(수백~수천 건)에 충분 |
| 생성 LLM            | **Qwen/Qwen3-4B-Instruct-2507** (로컬)                | 한국어 출력 자연스러움이 오픈소스 중 최상위 평가, 한국어 RAG 생성에 적합. Instruct 튜닝으로 "시드 정보로 추천 생성" 지시 수행 우수. 4B급이라 사양 부담 적당. Gemma 3 4B는 비교 후보 |

**기술 스택 관련 조언**

- 임베딩 모델은 arctic-embed-l-v2.0-ko로 시작하되, "최고"를 처음부터 고르려 애쓰지 말 것. sentence-transformers에서 이름만 바꾸면 교체됨. 파이프라인을 완성한 뒤 BGE-m3 등과 같은 시드로 비교하는 경험 자체가 핵심 학습 포인트. 최신 순위는 한국어 임베딩 리더보드 참고.
- 로컬 생성 LLM은 사양이 관건(GPU/VRAM). Qwen3-4B는 4B급이라 부담이 크진 않지만, 본인 장비로 돌릴 수 있는지(양자화 버전 포함) 미리 확인할 것.
- **4B급 가드레일**: 작은 모델은 어색한 문장·환각 위험이 상대적으로 큼. 프롬프트로 "주어진 시드 정보 안에서만 답하라"고 강하게 제약할 것. 이것이 "출처 충실성" 원칙의 실전 구현 지점.
- **생성 부분은 나중에 API로 갈아끼울 수 있게 코드를 추상화**해둘 것. 로컬로 만들되 품질이 아쉬우면 그 부분만 교체. (임베딩 교체와 같은 원리)
- LLM 후보 비교: Qwen3-4B-Instruct-2507(1순위) vs Gemma 3 4B. 같은 프롬프트로 추천 문장을 뽑아 비교. 한국 특화로 EXAONE 계열도 참고 가능.
- 모델 탐색법: Hugging Face Models에서 Task=Text Generation + Language=Korean 필터, Trending/Downloads 정렬. 다운로드 수·Community 활성도로 실사용 검증. Open Ko-LLM Leaderboard로 벤치마크 순위 확인.

## 5. 설계 관통 원칙

- **단순하게 시작, 확장 여지 남기기**: 모든 단계에서 MVP는 가볍게, 고도화는 다음으로. (협업형 입력, 대중교통 중점, 공간 클러스터링, API LLM 등이 모두 확장 슬롯)
- **각 도구를 강점에 맞게**: RAG는 분위기 의미 검색에 집중, 변동 잦은 가게 정보는 API에 위임, 거리 제약은 스코어링으로 보장.
- **데이터는 잘게, 집계는 유연하게**: 식당 단위+좌표로 저장해 식당/상권 양쪽 추천 가능성을 모두 열어둠.

## 6. 다음 할 일 (구현 착수 시)

1. 시작 상권 1곳 선정 → 식당 20~30개 시드 텍스트 작성(분위기 묘사 + 좌표 + 구조화 속성).
2. 카카오 로컬 API 키 발급, 텍스트→좌표 변환과 중간지점 계산 구현.
3. arctic-embed-l-v2.0-ko로 시드 임베딩 → Chroma에 메타데이터와 함께 저장.
4. 하이브리드 스코어링(분위기 유사도 + 정규화 거리) 검색 로직 구현, 가중치 변수화.
5. Qwen3-4B-Instruct-2507로 추천 설명 생성(시드 정보 제약 프롬프트 + 생성 모듈은 교체 가능하게 추상화).
6. 카카오맵 결과 표시 UI.
7. 파이프라인 완성 후: 임베딩 모델 비교, 가중치 튜닝, 나머지 상권으로 시드 확장.
